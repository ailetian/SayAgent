## 1. 切块策略决策树

```
文档类型？
  ├── Markdown 有标题层级
  │   └── MarkdownHeaderTextSplitter(headers=[("##","章节"),("###","小节")])
  │       + RecursiveCharacterTextSplitter(chunk_size=?, chunk_overlap=?)
  │
  ├── 纯文本 / PDF 文本提取
  │   └── RecursiveCharacterTextSplitter(chunk_size=?, chunk_overlap=?)
  │
  └── Excel / CSV 表格
      └── 逐行处理，每行转自然语言描述，再切块
```

**chunk_size 推荐：**

| 场景 | chunk_size | chunk_overlap | 原因 |
|------|-----------|---------------|------|
| 规章制度（如员工手册） | 800~1000 | 100~150 | 一个条款通常 200~500 字，大块保留上下文 |
| FAQ / 简短问答 | 300~500 | 50~80 | 问题和答案短，大块引入噪音 |
| 技术文档（API文档） | 500~800 | 80~120 | 一个函数/接口的描述通常在这个范围 |
| 长文章 / 报告 | 1000~1500 | 150~200 | 段落长，小块会切断论证链 |

**何时用小 chunk（300~500）：**
- 答案通常很短（1~3句话）
- 精确匹配比语义理解更重要
- 用户问"XX是什么"这类定义型问题

**何时用大 chunk（800~1500）：**
- 答案需要上下文才能理解
- 用户会问"为什么""怎么做"这类需要推理的问题
- 文档本身结构化程度低

## 2. 检索引擎选择

```
文档量 < 1000？
  ├── 是 → 纯向量检索足够（Chroma）
  │        如果查询含大量精确数字/代码 → 加 BM25 混合
  │
  └── 否 → 混合检索（BM25 + 向量）为标配
           文档量 > 10000 → 考虑加 Rerank
```

**三种方案的取舍：**

| 方案 | 成本 | 适用场景 | 不适用场景 |
|------|------|---------|-----------|
| 纯向量 | 最低 | 文档<1000，查询以语义为主 | 需要精确匹配数字/代码 |
| 混合(BM25+向量) | 低 | 大多数场景，兼顾精确和语义 | 文档极少（<50条）时无必要 |
| 混合+Rerank | 高 | 文档>10000，对准确率要求极高 | 文档量小、预算有限 |

**BM25 中文配置（必须）：**

```python
import jieba
BM25Retriever.from_documents(
    docs,
    k=TOP_K,
    preprocess_func=lambda t: list(jieba.cut(t))
)
```

不加 jieba = BM25 对中文无效。

## 3. RRF 融合参数

```
RRF 公式：score = Σ 1/(k + rank)

k 的推荐值：
  - k=60（默认）：大多数场景
  - k=30：文档量小（<100），希望排名更敏感
  - k=100：文档量大（>10000），希望排名更稳定
```

大白话：k 越小，排名越敏感（多往前一位加分更多）；k 越大，排名越稳定（各位置分差更小）。

## 4. Query Rewriting 决策

```
需要 Query Rewriting 吗？
  ├── 用户用口语提问？ → 需要
  ├── 有多轮对话历史？ → 需要（做指代消解）
  ├── 查询可能涉及同义词？ → 需要（改写时展开同义词）
  └── 纯关键词搜索？ → 不需要
```

---

## 5. Rerank 决策

```
加 Rerank 吗？
  条件1: 文档量 > 10000 → 强烈建议
  条件2: 检索结果中无关文档占比 > 30% → 建议加
  条件3: 对准确率要求严格，且预算允许 → 建议加

代价：
  - 每次查询多一次模型调用（延迟 +100~500ms）
  - 额外的模型部署或 API 费用
```

## 6. 多轮对话设计

```
需要多轮对话吗？
  用户会追问"那XX呢？""还有吗？" → 需要
  每次查询独立 → 不需要

多轮对话三要素：
  1. 对话历史存储（最近 6~10 轮）
  2. 指代消解（"那婚假呢？" → 上下文推断 + 改写为"婚假怎么申请？"）
  3. 话题切换检测（用户突然问无关话题时清空历史或用新话题覆盖）
```

## 7. Small-to-Big 检索（上下文窗口扩展）

```
大白话：用小块做检索（精准匹配），检索到后把前后块也一起喂给 LLM（完整上下文）。

为什么需要：
  切块时一个完整条款可能被切成 2~3 块
  → 检索只命中了其中 1 块
  → LLM 只看到片段，看不到完整的"如果...则...例外..."
  → 回答不完整或断章取义

做法：
  1. 每个 chunk 存的时候带上前后 chunk 的 ID
  2. 检索命中某个 chunk 后，自动获取它的前 1 块 + 后 1 块
  3. 合并后喂给 LLM
```

检索到 chunk_3 → 同时取 chunk_2 + chunk_3 + chunk_4 → 拼成大段上下文

代价：多取 2 个 chunk，LLM 输入 token 增加，但不增加检索复杂度。

## 8. 各优化手段到底提升什么（面试重点）

容易混淆的点：不同手段提升的是不同指标，不是一回事。

| 手段 | 提升什么 | 不提升什么 | 大白话 |
|------|---------|-----------|--------|
| **调整 chunk_size** | 召回率 | — | 块太小缺上下文，块太大噪音多 |
| **overlap** | 召回率（兜底） | — | 切偏了也能在相邻块找回来 |
| **混合检索(BM25+向量)** | 召回率 | 精确率 | 多一条路找到文档 |
| **Query Rewriting** | 召回率 | 精确率 | 口语→书面语，搜得更准 |
| **Rerank** | **精确率** | 召回率 | 粗筛10条→精筛3条，把无关的踢掉 |
| **Small-to-Big** | **回答完整度** | 召回率 | 搜到1块→补前后块，LLM看全貌 |
| **阈值过滤** | 精确率+拒答率 | 召回率 | 太差的就不答了 |

```
流程视角：

  用户问题
    → Query Rewriting ─────────→ 提升召回率
    → 混合检索 ────────────────→ 提升召回率
    → Small-to-Big(前后补全) ──→ 提升回答完整度
    → Rerank ─────────────────→ 提升精确率
    → 阈值过滤 ────────────────→ 提升精确率，兜底拒答
    → LLM 生成
```

关键澄清：
- **Rerank 不会提升召回率**，它只是在已经召回的 Top-K 里做排序，把最好的排前面。如果某段文档根本没被召回（在 Top-K 之外），Rerank 看不到它。
- **Small-to-Big 也不会提升召回率**，它不影响检索过程。它解决的是"搜到了但看到的不全"的问题。

## 9. 多路召回（Multi-Query Retrieval）

```
大白话：一个问题用多种问法各搜一遍，结果合并去重。

为什么需要：
  同一个意思，不同问法搜出来的结果可能不同
  "生病了工资怎么发？" 搜到的是病假规定
  "病假期间薪酬计算"    搜到的是薪酬福利章节
  → 两种问法合并，覆盖更全
```

**和混合检索的区别：**
```
混合检索：同一种问法 × 两种检索引擎（BM25 + 向量）
多路召回：多种问法   × 同一种检索引擎
两者叠加：多种问法   × 两种检索引擎  ← 最强，召回最广
```

**实现（3步，可以加到当前的 main.py 里）：**

```python
# [步骤1] 用 LLM 生成多个查询变体
def generate_query_variants(llm, question: str, n: int = 3) -> list[str]:
    prompt = f"""把以下问题改写成 {n} 个不同表述的查询，用于搜索文档库。
每行一个，覆盖不同的关键词和表达方式。

原问题：{question}
查询变体："""
    response = llm.invoke(prompt)
    return [q.strip() for q in response.content.strip().split("\n") if q.strip()]

# [步骤2] 每个变体各自检索
def multi_query_retrieve(question: str, variants: list[str]) -> list:
    all_results = []
    # 原始问题也搜一遍
    all_results.append(hybrid_retrieve(question))
    for v in variants:
        all_results.append(hybrid_retrieve(v))
    return all_results  # 多组结果

# [步骤3] RRF 合并所有结果
def merge_multi_query(all_results: list, top_k: int = 10):
    rrf_scores = {}
    doc_map = {}
    for result_group in all_results:
        for rank, (doc, label, _) in enumerate(result_group, 1):
            key = doc.page_content[:100]
            rrf_scores[key] = rrf_scores.get(key, 0) + 1.0 / (60 + rank)
            doc_map[key] = (doc, label)
    
    sorted_items = sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True)
    return [(*doc_map[key], round(score, 4)) for key, score in sorted_items[:top_k]]
```

**代价：**
- 多调用 1 次 LLM（生成变体）
- 多跑 N 次检索（每个变体各搜一次）
- 总延迟增加：LLM生成~1s + 检索变体数×检索耗时

**什么时候用：**
- 用户用口语提问，且单个查询改写后覆盖面不够
- 复杂问题需要综合多处信息
- 对召回率要求非常高的场景

**什么时候不用：**
- 查询已经很明确了（"年假几天"不需要多路）
- 延迟敏感（每次多等好几秒不值当）
- Query Rewriting 已经能覆盖大部分变体
