# RAG 上线前检查清单

> 逐项检查，全部通过 = 可以上线
> 每次发现新的上线前必查项 → 追加

---

## 安全

- [ ] API Key 通过环境变量加载，不硬编码在代码中
- [ ] `.env` 和 `chroma_db/` 已加入 `.gitignore`
- [ ] 用户输入做了基本的 Prompt Injection 过滤（检测"忽略之前的指令"等模式）
- [ ] 检索结果中如果有身份证号/手机号/工资等敏感信息，是否考虑脱敏
- [ ] 错误信息不向用户暴露内部实现细节（如"Chroma连接失败"应包装为"服务暂时不可用"）

## 检索质量

- [ ] 有相似度阈值过滤，检索结果太差时返回"不知道"而不是硬编
- [ ] 阈值经过实测验证（不是拍脑袋的值）
- [ ] 切块参数（chunk_size / overlap）匹配业务场景
- [ ] 中文场景下 BM25 配置了 jieba 分词
- [ ] 评测跑过，核心指标达标（召回率、Faithfulness 等）
- [ ] 至少覆盖了 3 种查询类型的测试用例

## 对话体验

- [ ] 用户问文档外内容时，系统明确表示"无法回答"而非猜测
- [ ] Query Rewriting 处理了口语化表达
- [ ] 多轮对话时做了指代消解（如"那XX呢？"）
- [ ] 回答中引用了来源，用户可以追溯到原始文档
- [ ] 回答长度适中，不过长（堆砌文档）也不过短（丢失信息）

## 性能

- [ ] Embedding 模型只加载一次（模块级复用，不每次查询重新加载）
- [ ] 向量库连接在启动时建立（不每次查询重连）
- [ ] P95 延迟符合目标要求
- [ ] 高频相同问题的答案考虑加缓存

## 运维

- [ ] 文档更新后有重建向量库的流程（`--init` 或脚本）
- [ ] 日志记录了关键步骤耗时（检索耗时、生成耗时）方便排查
- [ ] 有基本的监控指标暴露（检索量、延迟、拒答率）
- [ ] 用户反馈"踩"的记录有保存（用于后续优化）

## 代码质量

- [ ] 所有 LLM 调用有 try/except 兜底
- [ ] 关键参数集中管理（config.py 或 yaml），不散布在代码各处
- [ ] benchmark.py 可以从命令行直接运行
- [ ] 有 `requirements.txt` 或明确的依赖列表

## 文档

- [ ] 项目 README 写明了启动方式
- [ ] 配置参数的含义有注释说明
- [ ] 评测标准的目标值明确记录
