## 坑位 1：构建工具 Gradle ↔ Maven 不一致（P0）

**现象**：计划文档写"Gradle 8.8（§3）""`./gradlew test`"，但仓库实为 Maven。

**真相（务必以仓库为准）**：
- `backend/pom.xml` 存在，`backend/build.gradle` 不存在 ⇒ **Maven**。
- **本仓库没有 `mvnw` wrapper**（search 返回 0）。构建命令直接写 `mvn`（系统 Maven），**不要写 `../mvnw`**（M4 整改时误以为有 wrapper 而写 `../mvnw`，与真实态脱节，已勘误）。
- 计划文档位于 `plans/Mn/` 时，命令如 `cd backend && mvn test`。

**排查命令**：
- `list_dir backend` 看根，确认 pom.xml / build.gradle 谁在。
- `search_content` 在 `plans/Mn/`、`plans/0X_*` 搜 `gradlew|Gradle`，全改 `mvnw|Maven`。

**教训**：不要被文档里的"构建工具"声明带偏，先探仓库真实态。

**来源**：M3 验收实战

## 坑位 2：Flyway 迁移版本撞车（P1）

**现象**：新模块 DDL 脚本命名为 `V3__model_provider.sql`，直接撞车。

**真相**：`V3__user_created_at_index.sql` 已被占用（专门用于补偿 V2 漏建 `idx_created_at`）。新模块脚本必须顺延。

**MySQL 单序列顺延链（实测）**：V1(init)→V2(user)→V3(user_created_at_index)→V4(model_provider,M3)→**V5(agent,M4)**→**V6(document,M5)**→**V7(conversation,M6)**→**V8(conversation_log,M6)**→**V9(mcp_server,M7)**。
> M5 验收时源文档 `06_M5` 写 V5（撞 M4）、T1 写 V3（撞 M2）；M6 源文档 `07_M6` 写 V6/V7（撞 M5）；M7 写 V8（撞 M6）。一律按顺延链改。
**Pg 独立序列**：PostgreSQL+pgvector 走 `db/pg/migration/`，与 MySQL 版本号分开计数；V1=initdb（M1 `enable_vector`），M5 的 `knowledge_chunk`=V2。

**排查命令**：
- `list_dir backend/src/main/resources/db/mysql/migration/` 列出所有已占用版本号。
- 取最大号 +1 作为新脚本前缀；文档里所有版本引用一并核。
- `search_content` 在 plans 全目录搜 `V3__|V4__|migration/V3` 确认。

**教训**：Flyway 版本是全局唯一资源，先探目录再命名，禁止凭空写 V3。

**来源**：M3 验收实战

## 坑位 3：§6.1 DDL 模板漏 `idx_created_at`（P0，明令禁止复发）

**现象**：建表 SQL 漏了 `KEY idx_created_at (created_at)`。

**真相**：AGENTS.md §6.1 强制模板——**每张表都必须有** `KEY idx_created_at (created_at)`。用户明确要求"禁止再出现"。

**正确模板骨架**：
```sql
CREATE TABLE `xxx` (
  `id` BIGINT NOT NULL,
  ...
  PRIMARY KEY (`id`),
  KEY `idx_type` (`type`, `deleted`),
  KEY `idx_created_at` (`created_at`)   -- §6.1 模板强制
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

**排查命令**：
- `search_content` 在 plans 搜 `CREATE TABLE`，对每个表检查是否含 `idx_created_at`。
- 同时核对 `ENGINE=InnoDB`、`utf8mb4_0900_ai_ci`、主键、必要业务索引。
- DDL 不应带 `IF NOT EXISTS`（对齐 §6.1 模板）。

**教训**：文档里的建表/加索引 DDL，必须对照 §6.1 逐字段、逐索引核对，确保与规范一致（代码层是否真落实，留给「任务代码审核」查）。

**来源**：M3 验收实战

## 坑位 11：臆造符号 AppException/BizCode（类名不存在）（P0，根源级）

**现象**：M3/M4/M5 的 00_概述 + Tn 文档大量写 `AppException(BizCode.XXX)`（如 `AppException(BizCode.LLM_CALL_FAILED)`、`BizCode.NOT_FOUND`、`BizCode.UNAUTHORIZED`、`BizCode.EMBEDDING_FAILED`），但本仓库 `common/exception/` 下**根本不存在 `AppException` / `BizCode` 这两个类/枚举**（search 返回 0）。

**真相**：本仓库异常规范只有 `BizException`（`common/exception/BizException`，继承 RuntimeException）+ `ErrorCode` 枚举（`common/exception/ErrorCode`，AGENTS.md §3.5/§7.3）。`AppException`/`BizCode` 是通用 Java 脚手架的默认命名习惯，拆分时没回查仓库就套用了，属于"凭空臆造代码库不存在的类"。注意二级偏差：把 `BizCode.NOT_FOUND` 改成 `ErrorCode.NOT_FOUND` 后仍错——枚举里是 `MODEL_NOT_FOUND(1001)`（AGENTS.md §3.5 示例即 `MODEL_NOT_FOUND`），必须对齐真实枚举名。

**排查命令**：
- `search_content` 在 `backend/src` 搜 `AppException|BizCode`，确认仓库 0 命中（正统类是 `BizException`/`ErrorCode`）。
- `search_content` 在 `plans/Mn/` 全目录搜 `AppException|BizCode`，凡是命中即判不通过，统一改为 `BizException(ErrorCode.XXX)`。
- 改完后再搜一次 `NOT_FOUND`（无 `MODEL_` 前缀的裸 `NOT_FOUND`）等疑似臆造枚举名，对照 `ErrorCode.java` 真实枚举逐一核对拼写。

**教训**：写任何异常/错误码/类名前，必须先 `search_content` 仓库确认其真实存在且拼写一致；禁止套用通用脚手架命名。AGENTS.md §3.5 已新增"异常与错误码命名唯一性"硬性禁止 `AppException`/`BizCode`；拆分 skill 已加"符号落地"原则、验收 skill 已加"臆造符号"检测，二者互补拦截。

**来源**：M3/T2 开发验收发现（2026-07-23）

## 坑位 12：错引/臆造 AGENTS.md 章节与规范事实（P0，根源级）

**现象**：M3/T3 计划出现两类"凭通用认知臆造的规范/事实"：
- **错引章节**：第 21 行写"`§3.3`（规则4-6）：用 `@ConfigurationProperties` 强类型绑定，禁止 `@Value` 散落、禁止硬编码阈值"。但 `§3.3` 在 AGENTS.md 实际是"前端结构（Vue 3 + Vite）"，根本不是配置规范；且全文搜不到 `@Value`/`@ConfigurationProperties`/`规则4-6`。代码 `OkHttpConfig` 用 `@Value` 绑定 `hify.okhttp.*`，与 `JwtUtil`/`AdminSeedRunner` 等项目惯例一致，**完全合法**。
- **误判版本管理**：第 10/16/20/28 行称"Resilience4j 由 Spring Boot 父 POM 管理、禁止写死版本号"。但实测 `spring-boot-dependencies-3.3.5.pom` 中**无任何 resilience4j 条目**——父 POM 不管理该第三方依赖，`pom.xml` 必须显式写 `<version>2.2.0</version>`，否则 build 失败。

**真相**：这两处都是计划撰写时把"通用 Java/Spring 认知"当成"本仓库规范/事实"套用，属于"臆造不存在的规范章节"+"臆造与事实不符的版本管理假设"，与坑位 11（臆造不存在的类名）同源但更深一层（连章节号和父 POM 事实都错了）。

**排查命令**：
- 引用任何 `§X.Y` 前，先 `search_content` AGENTS.md 搜该章节号，确认**章节真实存在且主题与引用相符**（如 §3.3 是前端不是配置）。
- 声称"父 POM 管理某依赖版本"前，先核对本地 `.m2` 的 `spring-boot-dependencies-<boot版本>.pom` 是否含该 `<groupId>:<artifactId>` 条目；第三方库（resilience4j、jjwt 等）通常不在 Spring Boot BOM 里，须显式写版本。

**教训**：计划写"某章节规定/父 POM 管理"前，必须先查 AGENTS.md 真实章节与仓库真实态，**禁止把通用认知当本仓库规范**。AGENTS.md §3.4「版本纪律」仅针对 Spring 自家依赖，第三方库须显式固定版本。

**来源**：M3/T3 开发验收发现（2026-07-23）

## 坑位 13：跨库子查询不可执行（PG SQL 里子查询 MySQL 表）（P0）

**现象**：K4 计划给出"跨库软删下推"示例 SQL：在 **PG** 上执行的检索 SQL 里写 `WHERE document_id NOT IN (SELECT document_id FROM document WHERE deleted=1)`——但 `document`/`knowledge_base` 在 **MySQL**，PG 里根本没有这些表，照抄必报 relation does not exist。顺带列名也错（`SELECT kb_id FROM knowledge_base`，真实主键是 `id`）。
**真相（务必以仓库为准）**：双数据源架构（MySQL 业务 + PG 向量）下，**任何单条 SQL 只能落在一个库**。跨库过滤必须两段式：服务层先查 MySQL 得有效 id 集合，再作为命名参数（`:validKbIds`/`:validDocIds`）传入 PG SQL。
**排查命令**：对计划文本每段 SQL，先判定"这条 SQL 跑在哪个库"，再核对其中引用的每张表/每个列是否真在该库（对照 `db/mysql/migration/` 与 `db/pg/migration/` 的 DDL）。
**教训**：双库项目验收 SQL 时，第一问永远是"这条 SQL 在哪个库执行、引用的表都在这个库吗"。
**来源**：K 模块验收（2026-07-27）

## 坑位 14：部署镜像缺 PG 扩展 → Flyway 迁移必失败（P0，基础设施可落地性）

**现象**：K1 计划写 `V4__enable_zhparser.sql`：`CREATE EXTENSION IF NOT EXISTS zhparser`，但 `docker-compose.yml` 的 PG 镜像是官方 `pgvector/pgvector:pg16`——**不含 zhparser 二进制**。`CREATE EXTENSION`（即使 IF NOT EXISTS）在扩展未安装时直接报错 → Flyway 失败 → 应用启动失败；且与"zhparser 不可用自动降级"的探针设计自相矛盾（迁移炸了探针没机会跑）。
**真相（务必以仓库为准）**：`IF NOT EXISTS` 只防"已建过"，不防"没安装"。计划若引入新 PG 扩展，必须同步交付镜像改造（自建 Dockerfile 编译安装，或换含该扩展的镜像），或迁移脚本用 `DO $$ ... EXCEPTION $$` 容错并让探针降级。
**排查命令**：`grep image: docker-compose.yml`（及 `deploy/` 清单）核对镜像；对计划中每个 `CREATE EXTENSION`，确认镜像/基础设施真的带该扩展。
**教训**：验收不止查代码与规范，还要查"部署真实态"——迁移脚本依赖的基础设施能力必须有对应交付物闭环。
**来源**：K 模块验收（2026-07-27）

## 坑位 15：臆造扩展到"方法名/组件名"（坑位 11 的延伸）（P1）

**现象**：K 模块计划出现 `ProviderClient.chat()`（真实接口只有 `send()`/`stream()`/`embed()`）、`AuthAspect`（真实是 `AuthFilter`+`SecurityConfig`）、`ExecutorConfig`（真实是 `AsyncConfig`）、K3 谎称 `entity/DocumentChunk.java` 已有（chunk 在 pg 无 JPA 实体，走 `DocumentChunkRepository` 裸 SQL）。仓库检索均 0 命中。
**真相（务必以仓库为准）**：臆造不限于类名（坑位 11 的 AppException/BizCode），**方法名、配置类名、"已有"交付物声明**同样会被凭通用习惯编出来。凡计划声称"复用 M? 的 XXX"或标"已有"，必须逐个 `grep` 仓库确认符号与路径真实存在。
**排查命令**：对计划中每个「复用/已有」符号：`grep -rn "<符号名>" backend/src/main/java`；接口方法用 `grep -n "方法名(" <接口文件>` 核对签名。
**教训**：验收臆造检测的检索清单要覆盖：类名、方法名、配置类名、标"已有"的文件路径 4 类。
