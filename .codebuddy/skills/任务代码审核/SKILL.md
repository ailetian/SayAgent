# 任务代码审核（代码已合入后 · 自进化沉淀）

## 目的
把"代码已合入后，按 CLAUDE.md 审核真实仓库代码"时反复踩到的坑集中沉淀为单一事实源，让每次代码审核都能照单规避；并在审核过程中发现**新坑**时，自动写回本 skill 的 `references/代码审核避坑.md`，使 skill 随项目持续进化。

## 与「子模块任务拆分验收」的边界（务必分清）
| 维度 | 子模块任务拆分验收 | 本 skill（任务代码审核） |
|------|-------------------|--------------------------|
| 时机 | 计划文档**写完、编码前** | 代码**已合入仓库后** |
| 对象 | `plans/Mn/*.md` 计划文档 ↔ CLAUDE.md | 仓库真实代码 ↔ CLAUDE.md |
| 目的 | 让"照着做"的任务书本身合规 | 抓实际代码里的违规（功能对 ≠ 合规） |
| 坑的类型 | 文档层（章节号、Flyway 版本、包路径…） | 代码层（软删未生效、测试连真库、注释错引…） |

两者**互补、不混用**：计划文档阶段用「子模块任务拆分验收」；合入后的代码审核用本 skill。

## 何时使用
- 用户要求"审核代码""review 合入的代码""检查代码是否符合 CLAUDE.md""验收代码"。
- 某子模块代码已 merge，要确认其确实符合规范（而非"能跑就行"）。
- 触发词：代码审核、review 代码、合规检查、验收代码、坑。

## 使用方式
1. **审核前必读**：先 `read_file` 本 skill 的 `references/代码审核避坑.md`，通读全部代码层坑位，按图索骥提前排查。
2. **必验真实代码（核心纪律）**：`read_file` / `search_content` 真实仓库文件，逐条对照 CLAUDE.md 相关 `§x.y`。**绝不止于看计划文档或"构建绿/测试绿"**。
3. **"跑通"不等于"合规"，且"改完"更不等于"测过"**：测试绿、构建成功只证明功能对，**不证明符合规范**；而"我改了代码、lint 无错"连"功能对"都还没验证，绝不能据此宣布"审核通过"。审核点必须写成"规范符合性检查 + 实跑验证"（如"实跑测试确认不连真库或已登记规则35例外""实跑查询断言 `deleted=0` 过滤真生效并看 SQL 确认"），而非"用例绿即可"或"代码改完即可"。
4. **整改对象要正确**：文档错改文档、代码错改代码，别反。判定前先用 `search_content`/`read_file` 确认真实态，避免误报。
5. **发现新坑 → 自进化**（见下节）。

## 核心纪律（来自实战，勿犯）
- **必验代码**：审核绝不止于"计划文档 ↔ 规范"，必须 `read_file`/检索真实仓库文件对照规则。test green ≠ 合规。
- **没实跑测试，绝不说"审核通过"**：这是刚性红线。审核结论必须基于**真实跑过的测试/SQL 输出**，不可仅凭"代码已改、lint 无错、构建绿"就断言通过。尤其软删、规则35例外等点，必须实跑验证（见坑位1/3/5/6）。"我改了代码、看起来对"≠"已验证通过"。
- **不假设合规**：已 merge 的代码默认"可能仍违规"，逐条核实（如 `BaseEntity` 注释写"§6.1"不代表 `deleted=0` 过滤真生效）。
- **改错对象原则**：文档写错→改文档；代码写错→改代码。先定哪边错，再动手。
- **以仓库为真相源**：软删是否生效、测试是否连真库、注释章节引用是否对，一律以仓库真实态为准（含实跑输出为准）。

## 自进化协议（每次发现新坑都执行）
当在本 skill 的代码审核中发现**本库尚未收录的新坑**（新现象、新违规模式、新误报类型等），必须把它沉淀回本 skill，使其进化：
1. `read_file` 当前 `references/代码审核避坑.md`，找到末尾坑位最大编号 N。
2. 在该文件末尾**追加**新坑位，编号为 **N+1**，严格遵循既有格式：
   ```
   ## 坑位 N+1：<一句话标题>（<严重级 P0/P1/P2/P3>）

   **现象**：<在代码审核中观察到的错误表现>
   **真相（以仓库/CLAUDE.md 为准）**：<根因与正确做法>
   **排查命令**：<可复用的 search_content/list_dir/read_file 命令>
   **教训**：<一句话可复用结论>
   **来源**：<发现于哪次代码审核，如 Mx/Ty 2026-MM-DD>
   ```
3. 更新文件顶部"坑位索引"表，新增一行（编号 / 标题 / 严重级）。
4. 若新坑影响本 SKILL.md 的"核心纪律"或自查逻辑，同步补一句。
5. 不删除旧坑位（历史沉淀有价值）；只在末尾追加或修订既有条目的"真相/教训"。
6. 沉淀后向用户简要说明"新增坑位 N+1：xxx"，保持透明。

> 自进化不是可选步骤：每次代码审核收尾时，主动回想"这次有没有踩到清单外的新坑"，有则写回。
