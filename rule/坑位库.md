## K1. Windows 中文路径下 mvn spring-boot:run 失败

- **现象**：在路径含中文的工程（如项目路径含中文）下执行 `mvn spring-boot:run`，报 `ClassNotFoundException: com.hify.hify.HifyApplication`；日志里中文路径变成乱码（如 `AI鎺㈢储瀹為獙瀹`）。
  - 注意：`mvn test` / `mvn package` / `java -jar` **不受影响**（T6、T7 已两次实测踩坑）。
- **根因**：`spring-boot:run` 会 fork 一个「子 JVM」来跑主类；Windows 下该子 JVM 默认 `sun.jnu.encoding=GBK`，把 `-cp` 里含中文的工程路径错误解码，从而找不到 `target/classes` 里的主类。而 `java -jar` 跑的是 fat jar，内部 classpath 不含中文路径，故正常。
  - **与「乱码≠失败」的区别**（AGENTS.md §9）：此处是**真的失败**（启动不了），不是显示乱码。
- **解决方案**（按推荐度排序）：
  1. **【推荐】本地启动一律用 `java -jar`**：
     ```powershell
     cd backend
     mvn -DskipTests package
     java --% -Dfile.encoding=UTF-8 -jar target\hify-backend-0.0.1-SNAPSHOT.jar
     ```
     > **PowerShell 注意**：`-Dfile.encoding=UTF-8` 会被 PowerShell 解析器吞掉（见 K2），务必加 `--%`；若用 cmd（命令提示符）则无需 `--%`，直接写原命令即可。
  2. **【备选】坚持用 `spring-boot:run`**：必须给 fork 子 JVM 传 `-Dsun.jnu.encoding=UTF-8`：
     ```powershell
     cd backend
     [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
     $env:MAVEN_OPTS = "-Dfile.encoding=UTF-8"
     mvn spring-boot:run -Dspring-boot.run.jvmArguments=-Dsun.jnu.encoding=UTF-8
     ```
  3. **【治本】彻底消除中文路径编码问题**（二选一）：
     - 开启 Windows「设置 → 时间和语言 → 语言 → 管理语言设置 → 更改系统区域设置 → 勾选 使用 Unicode UTF-8 提供全球语言支持」后重启；
     - 或将工程移动到纯英文路径（如 `D:\projects\hify_python`）。
- **实测记录**：T6、T7 两次踩坑，`java -jar` 稳定通过；`mvn spring-boot:run` 即便设 `MAVEN_OPTS=-Dfile.encoding=UTF-8` 仍失败（根因是 `sun.jnu.encoding` 而非 `file.encoding`）。
- **关联**：AGENTS.md §9（编码规范）、README「本地跑通」启动章节。

## K2. PowerShell 中 `java -Dxxx=yyy -jar` 的 `-D` 参数被吞掉

- **现象**：在 PowerShell 中执行 `java -Dfile.encoding=UTF-8 -jar target\hify-backend-0.0.1-SNAPSHOT.jar`，报：
  ```
  错误: 找不到或无法加载主类 .encoding=UTF-8
  原因: java.lang.ClassNotFoundException: /encoding=UTF-8
  ```
  jar 正常、命令本身没错，但 `-Dfile.` 这段被 PowerShell 解析器吞掉，Java 把残串 `.encoding=UTF-8` 当成了「主类」。
- **根因**：PowerShell 解析命令行时，会把「以 `-` 开头、中间带 `.` 和 `=`」的整串参数（如 `-Dfile.encoding=UTF-8`）当作待解析 token，丢失 `file` 段。与 K1 的 `sun.jnu.encoding` 根因无关，是 PowerShell 原生参数解析的坑。
  - **与 K1 的关系**：K1 推荐「本地启动用 `java -jar`」，但其示例里的 `java -Dfile.encoding=UTF-8 -jar ...` 在 **PowerShell** 下正会触发本坑（该示例在 **cmd** 下正常）——故 K1 推荐命令已补 `--%`（见上）。
- **解决方案**（PowerShell 下任选其一）：
  1. **【推荐】`--%` 停止解析运算符**：让 `--%` 之后的内容原样传给 java（已实测启动 + `/actuator/health` 返回 UP 通过）：
     ```powershell
     cd backend
     java --% -Dfile.encoding=UTF-8 -jar target\hify-backend-0.0.1-SNAPSHOT.jar
     ```
  2. **`&` 调用运算符 + 引号包参**：把 `-D` 参数作为独立字面量传入：
     ```powershell
     & java '-Dfile.encoding=UTF-8' -jar 'target\hify-backend-0.0.1-SNAPSHOT.jar'
     ```
  3. **直接用 cmd（命令提示符）**：cmd 不做上述解析，`-D` 参数原样生效：
     ```cmd
     cd /d <项目根>\backend && java -Dfile.encoding=UTF-8 -jar target\hify-backend-0.0.1-SNAPSHOT.jar
     ```
  4. **可省略 `-Dfile.encoding=UTF-8`**：该参数只影响控制台中文是否乱码（属「乱码≠失败」，见 K1/§9），不影响功能；仅做健康检查时可直接省掉。
  - **注意**：`--%` 仅 PowerShell 有效，在 cmd 里会被当作参数传给 java 导致失败；跨 shell 请用方案 2 或 3。
- **实测记录**：T7 验收时用户踩坑，三个方案均实测可启动；`--%` 方案下 `/actuator/health` 返回 `UP` 且 `db`/`redis` 组件均 `UP`。
- **关联**：K1（中文路径 `mvn spring-boot:run` 失败）、AGENTS.md §9（编码/乱码≠失败）、README「本地跑通」启动章节。

## K3. 前端 flex 滚动容器缺 min-height:0 → 不自动跟随 / overflow 不生效

- **现象**：聊天等新消息进滚动区时，内容出现在可视区之外，需手动拖纵向滚动条才能看到最新；`scrollBottom()` 里 `el.scrollTop = el.scrollHeight` 设了等于没设。
- **根因**：滚动容器（如 `.chat-scroll`）是 flex 布局的子项，且**未设 `min-height: 0`**。flex 子项默认 `min-height: auto`，浏览器会用「内容高度」撑开该子项、而非把它约束为父容器分配的可视高度，导致 `overflow: auto` **实际不生效**（没有真正溢出），于是自动滚动代码把 `scrollTop` 设到「等于自身可视高度」的位置，看起来就是「没滚」。
- **解决方案**（聊天场景已落地）：
  1. **滚动容器加 `min-height: 0`**（关键），让它被约束为可视高度、内部真正可滚动；
  2. flex 布局（如 `display:flex; flex-direction:column; gap`）下移到一个内部包裹层（`.chat-list`），滚动容器本身只做 `overflow:auto`；
  3. 用 `ResizeObserver` 监听消息区高度变化 → 内容（含异步渲染的 markdown/代码块）一撑高就自动 `scrollTo({ top: scrollHeight })`；
  4. 「底部守卫」：仅当用户已在底部附近（距底 < 80px）或正在流式生成时才自动跟随，用户上滑看历史时不强行拉回。
- **通用规律**：**任何「flex 子项 + overflow:auto 想内部滚动」的容器，都必须加 `min-height: 0`**（纵向）或 `min-width: 0`（横向）。这是 flexbox 最常被忽略的必设项，也是 Chat.vue 滚动失效的唯一根因。
- **实测记录**：`frontend/src/views/Chat.vue` 按上述修复，`npm run build` 通过，用户硬刷新后新消息/流式回复自动滚到底。
- **关联**：AGENTS.md §3.3（前端结构）、§3.7（前端单文件规模/模块化，防止重灾区）、§11 本索引。

## K4. 后端重复实例抢同一端口 → 前端整页 15s 超时（端口监听但不服务）

- **现象**：登录后 Agents/Models/McpServer 等多个页面的 `load()` 与对话/历史接口全部 `Uncaught (in promise) Error: timeout of 15000ms exceeded`；登录页能渲染、但所有数据接口卡 15s；对话列表很久才出、点开对话历史不加载。
- **根因**：存在**多个后端 Java 进程以同一 `--server.port`（本机 9095）启动**，互相抢端口。其中「抢到端口的那个」能 accept 连接，但另一个处于「端口在监听、应用上下文却没正常起来/半死」状态——它接受 TCP 连接却永远不回 HTTP 响应，于是前端每个请求都被挂起直到 axios 15s 超时。前端 Vite（`http://localhost:6177`）把 `/api` 代理到 `http://localhost:9095`，所以**全部接口一起超时**。
- **排障步骤**（实测有效）：
  1. 直连后端端口看是否真在服务：`curl -m 8 http://localhost:9095/`，若 **HTTP=000 且 8s 无响应** = 「端口监听但不服务」；
  2. 列监听端口与进程：`Get-NetTCPConnection -LocalPort 9095 -State Listen` + `Get-CimInstance Win32_Process -Filter "Name='java.exe'"`，找重复 `java -jar ... --server.port=9095` 进程；
  3. **杀掉重复进程、只留一个**，确认端口 `FREE` 后干净起单实例；
  4. 重启前确认 jar 内迁移脚本齐全（`jar tf ...jar | grep migration`），否则 Flyway 校验失败导致启动中止。
- **预防（开发/运行纪律，硬规则）**：
  - **同一后端只起一个实例**；启动前先确认目标端口未被占用；
  - 勿在多终端 / 多脚本里重复执行 `java -jar ... --server.port=9095`；
  - 若用后台任务或 `&` 启动，先 grep 端口确认没有已存在的同端口实例再起；
  - 改完代码重建 jar 后，先停旧实例再起新实例，不要叠加。
- **实测记录**：杀掉重复 PID 159004 / 204100 → 单实例 PID 216436 起在 9095 → `curl /actuator/health` 200(12ms)、经 Vite 代理 `/api/agents` 401(8ms)，响应从 15s 卡死变毫秒级。
- **关联**：AGENTS.md §5（部署/单端口）、§10（子任务交付，重建 jar 后要先停旧实例）、§11 本索引。
