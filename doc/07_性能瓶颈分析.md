# SayAgent 性能瓶颈分析

> 基于：《05_部署架构设计.md》（Spring Boot 单体 + Vue + MySQL + Redis + pgvector，50 人内部，重度依赖外部 LLM）
> 文档版本：v1.0
> 日期：2026-07-19
> 关联文档：《04_外部LLM调用技术方案.md》《05_部署架构设计.md》

---

## 1. 核心特征

用户感知的延迟几乎全被"外部 LLM 调用"主导，传统 Web 瓶颈（DB、应用吞吐）相对次要。瓶颈分析据此排序。

---

## 2. 瓶颈严重程度排序

| 排名 | 瓶颈 | 为什么是瓶颈 | 触发条件 | 一期(50人)是否处理 |
|---|---|---|---|---|
| 1 | **外部 LLM 延迟 / 限流 / 不稳定** | 每次对话都卡在等外部大脑，秒~几十秒；并发高就 429/超时，且无法提速只能治理 | 任意对话；>配额 QPS 或某提供商抖动即触发 | **必须（已有 04 方案，需落实）** |
| 2 | **并发慢调用耗尽线程 / 连接** | 50 人若同时对话，每个 SSE 挂几十秒；Tomcat 线程、DB 连接池、LLM 线程池任一过小都会堵死 | 峰值并发 > 池容量（如 >20 同时对话且池配小） | **需要基础配置**（池大小 + 虚拟线程 + 异步写库） |
| 3 | **Nginx/SSE 缓冲与超时配置不当** | 默认缓冲会让流式"攒批"卡顿，超时过短会断流 | SSE 未关 `proxy_buffering` 或 `proxy_read_timeout` 太短 | **需要（改配置即可，成本低）** |
| 4 | **pgvector 检索变慢** | 向量查询未建索引/量大时检索延迟上升，拖慢 RAG | 知识库文档量大（数万+片段）且高并发检索 | 基本不需要（量小，建好向量索引即可） |
| 5 | **MySQL 写入/连接压力** | 每条消息同步写库会拖慢 SSE 返回；连接池小会阻塞 | 高频对话 + 每消息写库 + 池配小 | 轻量处理（连接池 + Redis 缓存配置 + 异步落库） |
| 6 | **Redis 单点** | 缓存/限流/会话都压它，故障影响面大 | Redis 挂且无可降级路径 | 不需要专门处理（单实例+持久化足够） |
| 7 | **文档批量 embedding 耗时** | 上传大文档批量向量化慢，占 CPU/耗时 | 大文档上传（离线任务，不影响对话） | 不需要（异步队列处理即可） |

---

## 3. 各瓶颈说明与一期做法

### ① 外部 LLM 延迟/限流（最严重，非可消除）
- **机制**：系统天花板，SayAgent 只是"中转 + 增强"，生成快慢由外部决定。
- **一期做法**：严格落实《04》Resilience 管线（超时 + 重试 + 熔断 + 备用链降级）+ RateLimiter 防 429；用流式 SSE 让用户"边生成边看"，体感更快。一期唯一必须做扎实的。

### ② 并发慢调用吃线程/连接
- **机制**：慢 I/O 若占着 Tomcat 线程，几十并发就 502。
- **一期做法**：`SseEmitter` + 专用 `llmExecutor` 线程池（或 Java 21 虚拟线程）；HikariCP 连接池调到合理值（如 20-50）；对话记录**异步写库**，不阻塞 SSE 返回。50 人峰值约 10-20 并发，池配好足够。

### ③ Nginx/SSE 缓冲
- **机制**：默认 `proxy_buffering on` 把流攒成块再发，用户看到"卡一下蹦一段"。
- **一期做法**：`proxy_buffering off; proxy_read_timeout 120s; proxy_send_timeout 120s;`（见《05》）。改配置即可，必做。

### ④ pgvector 检索
- **一期不做优化**：内部文档量小，建好向量索引（HNSW/IVFFlat）即可；真到几千人、文档海量再调参/分片。

### ⑤ MySQL 写入
- **一期轻量**：配置连接池、用 Redis 缓存 Agent/模型配置减少查库、消息落库改为异步（发完再写）。

### ⑥ Redis 单点 / ⑦ 批量 embedding
- **一期都不需要专门处理**：单实例 + AOF 持久化够用；embedding 走异步任务，不进对话热路径。

---

## 4. 结论（一期重点）

一期真正要落实的三件事，均已在前面文档规划：
1. **LLM 调用治理**（《04》：超时/重试/熔断/降级/限流）—— 体验与安全核心。
2. **线程与 SSE 配置**（《02》《04》《05》：专用线程池或虚拟线程 + Nginx 流式配置）—— 防堵死。
3. **异步落库 + 配置缓存**（轻量）—— 别让 DB 拖慢对话。

其余（pgvector 调优、Redis 高可用、embedding 并行）在 50 人规模下**不必动**；架构已通过"向量库与业务库分离 + 无状态单体可扩容"提前规避。
