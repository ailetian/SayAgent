# 09_数据库性能规范（MySQL 8.x 业务库）

> 一句话结论：这是给 SayAgent 的 MySQL 业务库定的「建表与查询交通规则」——让表不会因为聊天记录暴涨而变慢，也让 AI 帮你建表时照着做就不踩坑。
> 重要事实：按 `05_部署架构设计.md`，**业务关系数据在 MySQL，向量在 pgvector（PostgreSQL 的扩展）**。两者是分开的两个库。本规范针对 MySQL 业务表；向量索引在 pgvector 侧用 HNSW，见第 6 节。

---

## 1. 通用字段约定（所有表都套用）

**标准表头模板（建任何表都先复制这段）**：

```sql
CREATE TABLE `example` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `created_at`  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  `updated_at`  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  `deleted`     TINYINT(1) NOT NULL DEFAULT 0 COMMENT '软删除标记 0未删 1已删',
  PRIMARY KEY (`id`),
  KEY `idx_created_at` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='示例表';
```

**约定点（人话解释）**：
- `id` 用 **BIGINT 自增**，不要用 UUID 当主键（UUID 乱序会让索引碎片、插入变慢）。
- `created_at` / `updated_at` 自动维护；查"某天起的记录""最近更新"都靠它们。
- `deleted` **软删除**：不真删数据，查询时加 `WHERE deleted=0`，既防误删又便于审计/恢复。
- 统一 `utf8mb4`（能存 emoji 和生僻字）、`InnoDB`（支持事务、行锁）。

## 2. 索引设计原则

**规则清单（AI 建表时逐条核对）**：
1. 主键用自增 `BIGINT`，避免 UUID 主键。
2. 所有「外键列」（如 `user_id`、`agent_id`）**必须建索引**，否则按人/按 Agent 查会变全表扫描。
3. 高频 `WHERE` / `ORDER BY` 列建索引；多条件用「联合索引」且**区分度高的列放最前**（最左前缀原则）。
4. 单表索引不超过 5~6 个，多了写入会变慢（写放大）。
5. 长字符串（如 `name`）用「前缀索引」：`INDEX(name(50))`，不要整列建索引。
6. 状态/类型等低区分度枚举列，不单独建索引，放联合索引末尾即可。
7. 不在 `TEXT`/`MEDIUMTEXT` 上建普通索引（太大）；需检索交给 pgvector 或全文索引。

**示例（对话相关表，含正确索引）**：

```sql
CREATE TABLE `conversation` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`    BIGINT UNSIGNED NOT NULL COMMENT '发起用户',
  `agent_id`   BIGINT UNSIGNED NOT NULL COMMENT '所属 Agent',
  `title`      VARCHAR(255) DEFAULT '' COMMENT '会话标题',
  `created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  `deleted`    TINYINT(1) NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_user_agent` (`user_id`,`agent_id`,`deleted`),
  KEY `idx_created_at` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='会话表';

CREATE TABLE `message` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `conversation_id` BIGINT UNSIGNED NOT NULL COMMENT '所属会话',
  `role`           TINYINT NOT NULL COMMENT '1用户 2助手 3系统',
  `content`        MEDIUMTEXT COMMENT '消息内容',
  `token_count`    INT UNSIGNED DEFAULT 0 COMMENT '消耗 token',
  `created_at`     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  `deleted`        TINYINT(1) NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_conv_created` (`conversation_id`,`deleted`,`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='消息表';
```

> 说明：`message` 主要按「某个会话 + 时间」查，联合索引 `(conversation_id, deleted, created_at)` 正好覆盖该查询，且符合最左前缀。

## 3. 大表预判与应对策略

**AI 平台哪些表会变大**：
| 表 | 增长来源 | 量级预判 | 重点 |
|---|---|---|---|
| `message` | 每轮对话 1~2 行 | 50人 × 日均数十 × 365 ≈ 十万~百万级/年 | **中到大表，重点防范** |
| `conversation` | 每会话一行 | 较小 | 一般 |
| `knowledge_chunk` | 知识库切分 | 随文档增长，可控 | 向量在 pgvector |
| `token_usage` | 只增 | 小 | 汇总即可 |

**应对策略**：
1. **分区**：`message` 按 `created_at` 做 RANGE 分区，旧数据查询快、易归档。
   ```sql
   CREATE TABLE `message` (
     `id` BIGINT UNSIGNED NOT NULL,
     `conversation_id` BIGINT UNSIGNED NOT NULL,
     `role` TINYINT NOT NULL,
     `content` MEDIUMTEXT,
     `token_count` INT UNSIGNED DEFAULT 0,
     `created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
     `updated_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
     `deleted` TINYINT(1) NOT NULL DEFAULT 0,
     PRIMARY KEY (`id`, `created_at`)   -- 分区表主键须含分区键
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
   PARTITION BY RANGE (TO_DAYS(created_at)) (
     PARTITION p2026 VALUES LESS THAN (TO_DAYS('2027-01-01')),
     PARTITION p2027 VALUES LESS THAN (TO_DAYS('2028-01-01')),
     PARTITION pmax  VALUES LESS THAN MAXVALUE
   );
   ```
2. **归档**：超过 1 年的消息搬到 `message_archive` 冷表或对象存储，热表只留近期。
3. **不实时 COUNT**：列表页「总消息数」别用 `COUNT(*)` 扫大表，用汇总表异步更新，或只显示「是否有更多」。
4. **内容不索引**：`content` 用 `MEDIUMTEXT`，不建普通索引；语义检索交给 pgvector。
5. **容量预警**：监控 `message` 行数，接近百万时评估分表或清理。

## 4. 分页查询注意事项

**错误写法（深分页慢）**：
```sql
SELECT * FROM message ORDER BY id DESC LIMIT 100000, 20;  -- offset 越大越慢，全表扫
```

**正确写法（游标 / keyset 分页）**：记住上一页最后一条的 `id`，下一页接着查：
```sql
SELECT * FROM message
WHERE conversation_id = ? AND deleted = 0 AND id < :last_id
ORDER BY id DESC LIMIT 20;
```

**要点（人话）**：
- 前端「下一页」传 `last_id`，**不是传页码**。
- 永远带 `ORDER BY` + 索引列过滤，才能命中 `idx_conv_created`。
- 列表页不显示精确总数；用「还有更多」近似（探测或上次汇总值）。
- 管理后台若需跳页，限制最大偏移（如不超过 1000）或改用时间范围筛选。

## 5. AI 建表可执行模板（直接照抄的指令）

> 给 AI（或你自己）建任何业务表时的统一约束，先读这段再写 DDL：

- 引擎 `InnoDB`、字符集 `utf8mb4`、排序 `utf8mb4_0900_ai_ci`。
- 必有四字段：`id`(BIGINT 自增)、`created_at`、`updated_at`、`deleted`(软删)。
- 凡外键列建索引；多条件查询建联合索引（高区分度列在前）；不在 TEXT 建普通索引。
- 预估会大的表（消息/日志类）使用**分区 + 归档**策略。
- 分页一律 **keyset**，禁止深 `LIMIT offset`。
- 向量/语义检索不放 MySQL，交给 pgvector（见第 6 节）。

## 6. 向量索引（pgvector 侧，补充说明）

pgvector 不在 MySQL，跑在独立的 **PostgreSQL** 实例（与 `05` 部署一致）：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE knowledge_chunk (
  id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  doc_id    BIGINT,
  content   TEXT,
  embedding vector(1536)   -- 维度随 embedding 模型而定
);
-- HNSW 向量索引，余弦相似度
CREATE INDEX idx_chunk_vec ON knowledge_chunk
  USING hnsw (embedding vector_cosine_ops);
```

说明：向量相似检索走 HNSW 索引；维度 `1536` 等按你用的 embedding 模型定（如 OpenAI `text-embedding-3-small` 为 1536，需与实际配置一致）。
