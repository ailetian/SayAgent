# Hify 功能需求文档

> 项目定位：基于 Dify 思路、面向团队内部的简化版 AI Agent 平台
> 文档版本：v1.0
> 日期：2026-07-18
> 技术选型（已定型）：**Spring Boot + Vue**，详见《02_技术选型文档.md》

## 1. 项目背景与约束

| 约束项 | 说明 |
|---|---|
| 开发资源 | 单人开发（从 0 到上线全栈负责） |
| 使用对象 | 团队内部 20-50 人 |
| 部署方式 | 本地部署（单租户、自托管） |
| 设计原则 | 砍掉一切"商业化 / 生态市场 / 超大规模 / 进阶运维"类复杂度，只保留让团队用起来的最小闭环 |

### 1.1 项目目标与意义

本项目并非单纯"给团队找个能用的 AI 助手"——若仅为此目的，直接部署 Dify 私有版即可满足。Hify 的核心目标定位为：

- **练出一套全栈 AI 平台真本事**：从 LLM 调用治理、RAG 全链路、Agent 编排、MCP 接入、流式交互到前后端全栈与 Docker/K8s 部署，完整走一遍，形成可迁移的工程能力。
- **完全自主可控**：每个模块、每处代码、每份数据都在自己手里，可审计、可改造，不绑定任何外部 SaaS 的能力边界。
- **支持后期深度定制与维护**：随团队真实使用情况，对模型接入、知识检索、工具调用、工作流等做精细化定制，扩展空间完全由自己掌握。

> 因此，技术选型上接受"不会 Java 仍用 Spring Boot"的学习成本（视其为必要的工程化学费）；功能范围上保留主干、砍掉非核心（见第 2/3 节）；整体以"学得会、改得动、控得住"为第一准则。本目标由开发者于 2026-07-20 明确确认。

## 2. 必须做（核心 MVP）

构成主链路：**登录 → 配模型 → 建 Agent → 挂知识 → 对话/API → 留日志 → 本地部署 + MCP 接内部系统**

| 序号 | 模块 | 说明 | 理由 |
|---|---|---|---|
| 1 | 基础登录 + 轻量权限 | 登录 + 管理员 / 用户两种角色 | 20-50 人内部使用必须区分"谁能管模型 / 知识"，轻量鉴权即可，开发量小 |
| 2 | 模型管理（简化） | 管理员在后台**手动添加**模型：填名称、API 地址、秘钥、类型（OpenAI/Claude/Gemini/Ollama），可配 1-3 个 | 内部通常只用少数模型，做成手动配置页即可，无需多供应商市场 |
| 3 | Agent 配置（简化） | 提示词 + 选模型 + 挂知识 / 工具 | 平台核心价值，用表单式配置而非拖拽画布，单人可完成 |
| 4 | 知识库 + RAG | 文档上传、向量化、检索问答 | 内部团队最刚需场景（基于公司文档问答），直接复用现有库，是平台立足点 |
| 5 | 聊天 Web UI + 内部 API | 网页对话界面 + 供内部调用的 API | 覆盖 90% 使用场景，无对外发布需求，做到这层即可 |
| 6 | 对话日志（简化） | 记录谁、何时、问了啥、耗多少 token | 便于排查问题和控成本，一张日志表足够，无需复杂看板 |
| 7 | 单租户本地部署 | docker-compose 一键起 | 这是部署约束本身，且比多租户简单得多 |
| 8 | MCP 集成 | 支持以 Model Context Protocol 接入内部工具 / 系统 | 内部团队常需对接自有系统（数据库、内部 API、SaaS 等），MCP 是统一、低成本的接入标准，能让 Agent 直接调用内部能力，价值高且生态成熟 |

### 2.1 关键简化约定
- **Orchestration / Agent**：用表单 / 配置页实现，不做可视化拖拽画布。
- **模型管理**：管理员后台**手动添加**模型（填写名称 / API 地址 / 秘钥 / 类型），不做供应商切换市场，不做自动探测。
- **MCP**：做成"管理员配置 MCP Server 地址 → Agent 自动发现可用工具"的轻量模式，不做完整插件市场。

## 3. 砍掉（首版不做）

| 序号 | 模块 | 理由 |
|---|---|---|
| 1 | 可视化 Workflow 画布 | Dify 里开发量最大、最复杂的模块；内部场景用"对话 + 工具"已够，首版省掉，后续再加简单顺序链 |
| 2 | 插件市场 / Marketplace | 内部平台无需公开市场，改为硬编码几个常用工具即可，省掉整套市场系统 |
| 3 | 嵌入发布 / 公开分享 | 无对外发布需求，砍掉 iframe 嵌入和公开分享能力 |
| 4 | 高级 LLMOps（反馈循环 / 延迟分析 / 用量看板） | 20-50 人规模用不上复杂可观测体系，原始日志已够用 |
| 5 | Cloud / 多租户 / 计费 | 内部工具无商业化需求，直接去掉整套多租户隔离与计费系统，大幅减负 |
| 6 | 知识管道评测台 | 检索质量调优是进阶需求，首版用默认分块策略跑通即可，省掉评测 UI |

---

## 4. MVP 范围总结

- **必须做 8 项**，砍掉 6 项。
- 首版聚焦：让团队能登录、配模型、建 Agent、挂知识、通过网页 / API 对话、留日志，并通过 MCP 接入内部系统，全部本地单租户部署。
- 明确首版不做：可视化工作流画布、插件市场、嵌入发布、高级 LLMOps 看板、多租户 / 计费、知识管道评测台。

---

## 5. 技术选型（最终定型）

> **Spring Boot + Vue**

- 后端 Spring Boot 包揽全部能力：登录/权限、模型管理、Agent、RAG、MCP、对话日志。
- 前端 Vue 做配置页 + 聊天 UI。
- 前后端通过 SpringDoc 自动生成的 OpenAPI 契约对接。
- 构建用 Gradle/Maven，部署用 docker-compose。
- AI 能力通过 LangChain4j / MCP Java SDK 落地（详见《02_技术选型文档.md》第 6 节）。
- 选型理由与对比详见《02_技术选型文档.md》。
