# Hify 部署架构设计

> 约束：模块化单体；技术栈 Spring Boot + Vue + MySQL + Redis + pgvector；目标 50 人内部使用；生产环境 Docker + K8s 部署。

## 1. 组件清单与职责

| 组件 | 形态 | 职责 |
|---|---|---|
| **Nginx（Ingress）** | K8s Ingress / Deployment | 统一入口，HTTPS 终结、路由 `/api/*`→后端、`/`→前端静态资源、SSE 长连接超时放宽 |
| **Vue 前端** | 静态构建物，由 Nginx 托管 | 配置页 + 聊天 UI，纯静态，无后端逻辑 |
| **Hify 后端（Spring Boot 单体）** | K8s Deployment，无状态，2 副本 | 全部业务能力：模型管理、Agent、对话引擎(SSE)、RAG、工作流、MCP；调外部 LLM；靠 Resilience4j 做线程/超时/重试/熔断 |
| **MySQL** | K8s StatefulSet / 云托管 RDS | 业务主库：用户、Agent 配置、模型配置、对话记录、知识库元数据、工作流定义 |
| **Redis** | K8s StatefulSet / 云托管 | 缓存（模型配置、知识元数据）、限流计数、SSE 会话/发布订阅、可选对话上下文热缓存 |
| **pgvector（PostgreSQL 扩展）** | 与 MySQL 并存，或 PostgreSQL 实例开 pgvector | 向量存储：文档 embedding、相似检索（RAG 核心） |
| **对象存储 / 本地盘（文档）** | PV 或 S3 兼容 | 知识库原始文档文件存放（切分前/后） |
| **Config / Secret** | K8s ConfigMap + Secret | 数据库连接、LLM API Key、Redis 地址等，不入代码 |

> 说明：MySQL 管业务关系数据，pgvector 管向量——两者并存，避免把大向量塞进 MySQL 拖慢事务库。50 人规模向量量小，单 PostgreSQL 实例开 pgvector 足够。

## 2. 请求流转（两条主链路）

**链路 A：管理配置（低频）**
```
管理员浏览器 → Nginx → Vue 静态页 → Nginx(/api) → Hify 后端
   → MySQL（存 Agent/模型/工作流配置）
   → Redis（缓存配置，减少重复查库）
```

**链路 B：对话（高频、流式、核心）**
```
用户浏览器 → Nginx → Vue → Nginx(/api/chat/stream, SSE) → Hify 后端
   1. 后端从 Redis 取 Agent/模型配置（命中则免查库）
   2. conversation 引擎组装上下文
   3. 若需知识：查 pgvector 做相似检索 → 拼进 prompt
   4. ProviderRouter 选主用提供商，经 Resilience 管线（熔断/重试/超时）调外部 LLM
   5. token 逐条经 SseEmitter 推回 → Nginx 透传 → 前端渲染
   6. 完成后对话记录写 MySQL；调用计数/限流写 Redis
```

**链路 C：MCP 工具调用（对话中触发）**
```
对话引擎 → mcp 模块 → 内部 MCP Server（可部署在集群内或公司内网）
   → 返回工具结果 → 拼回 prompt 继续生成
```

## 3. K8s 部署结构（当前阶段）

```
Namespace: hify-prod
├── Deployment: hify-backend        replicas: 2   (无状态，HPA 可选)
│     envFrom: ConfigMap + Secret
│     probes: readiness/liveness (/actuator/health)
├── Deployment: hify-frontend       (Nginx 托管静态资源) 或并入 Ingress
├── Ingress: hify-ingress           (HTTPS, 路由规则, SSE 超时放宽)
├── StatefulSet: mysql              (PVC 持久化)
├── StatefulSet: redis              (PVC / 空密码仅内网)
├── StatefulSet: postgres-pgvector  (PVC 持久化, 开 pgvector 扩展)
├── ConfigMap: hify-config
└── Secret:    hify-secrets         (DB 密码, LLM Keys)
```

**关键配置点**：
- **副本数**：50 人内部，后端 2 副本即可（高可用 + 滚动发布零中断）；对话无状态，多副本天然水平扩容。
- **SSE 与 Ingress**：Nginx `proxy_read_timeout` / `proxy_send_timeout` 调到 120s+，关掉缓冲（`proxy_buffering off`），否则流式被攒批。
- **优雅停机**：Spring 配 `server.shutdown=graceful`，K8s `terminationGracePeriodSeconds` 留足，让在飞 LLM 调用完成、SSE 收尾。
- **外部 LLM 出网**：后端 Pod 需能访问公网 LLM API（或公司代理）；Ollama 若本地部署则放集群内或独立节点。
- **持久化**：MySQL/PostgreSQL/Redis 用 PVC；文档原始文件用 PV 或对象存储。
- **资源**：给后端设 requests/limits（如 1C2G 起步），避免 LLM 调用积压吃光节点内存。

## 4. 规模匹配说明

- 50 人内部，QPS 低，单体 2 副本 + 单机 MySQL/Redis/pgvector 完全够，不必上微服务。
- 模块化单体（Modulith）已画好包边界，将来某模块（对话/RAG）成瓶颈，可单独抽 Deployment，无需重写。
- K8s 当前价值主要是：声明式部署、滚动更新零中断、配置/密钥外置、副本高可用，而非弹性伸缩。

## 5. 模块大白话讲解（门外汉视角）

把整套系统想象成"一家公司"，各组件对应如下：

| 组件 | 大白话 |
|---|---|
| **Docker** | 把软件和它需要的运行环境一起打包成一个"集装箱"。好处是"在我电脑能跑，到你电脑也能跑"，不怕环境不一样。 |
| **Kubernetes（K8s）** | 管这些集装箱的"调度员"。哪个集装箱挂了它自动重启，人多就多开几个，还负责安排它们跑在哪台机器上。 |
| **Nginx / Ingress** | 公司"前台+保安"。所有访问先到它这，它决定把人领去前台(网页)还是办公室(后台)，还负责 HTTPS(门禁)和放行长连接。 |
| **Vue 前端** | 公司的"接待大屏/前台界面"。用户看到的按钮和聊天框都在这，它自己不干活，你点一下它就转告后台。 |
| **Spring Boot 后端（Hify 本体）** | 公司里"真正干活的办公室"。所有大脑逻辑都在这：配模型、配 Agent、跑对话、查知识、调内部工具。 |
| **MySQL** | "标准档案柜"。用表格存重要的、要长期准确的数据：账号、Agent 配置、对话记录。 |
| **Redis** | "桌面便签/速查小本"。存临时、要极快取到的东西：热门配置缓存、限流计数、实时会话。特点：快，但停电可能丢，适合临时数据。 |
| **pgvector** | "带智能检索的图书索引室"。它把文字变成一串数字坐标(向量)，能按"意思相近"找内容。RAG 靠它：你问问题→变向量→它找出最相关的文档片段。 |
| **对象存储/本地盘** | "文件仓库"。你上传的 PDF/Word 原始文档放这。 |
| **ConfigMap / Secret** | "配置信封+保险箱"。把数据库密码、API 密钥单独锁好，不写进代码里，换环境方便、也更安全。 |
| **外部 LLM（OpenAI 等）** | "外包的大脑公司"。Hify 自己不会思考，把问题发给它们，拿回回答。 |

## 6. 一次对话在"公司"里怎么走（通俗串联）

> 你（用户）走到前台 Nginx → 在接待大屏 Vue 上打字提问 → 前台把问题转给办公室 Hify 后端 → 办公室先翻便签 Redis（配置还要不要查档案？）→ 需要懂公司资料就去图书索引室 pgvector 找相关片段 → 然后打电话给外包大脑 LLM（经熔断/重试保护）→ 大脑一句句回答案，办公室通过 SSE 像"打电话直播"一样逐句传回你屏幕上 → 聊完，记录存进档案柜 MySQL，计数写便签 Redis。
